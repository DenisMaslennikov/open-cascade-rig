# Каскадный AI-конвейер разработки — журнал архитектурных решений

Обновлено: 2026-10-31. Единственный источник правды по **архитектуре** проекта.
История обсуждения — `session_search`. Инфраструктурные частности (как ставить и настраивать сервисы, эндпоинты, ловушки конфигов) — в скилах (`cascade-pipeline`, `github-actions-runner`, `cascade-new-project`), а не здесь.

## 0. Правила ведения журнала

- Сюда попадает только решение, меняющее архитектуру: границы ролей и компонентов, контракты между ними, инварианты, модель ветвления и ревью, схема хранения состояния и денег, выбор основы. Всё, что «как запустить/настроить», — в скилы и в `PLAN.md`.
- Запись вносится **после явного согласия владельца**: агент предлагает формулировку, владелец одобряет. Без «да» — не пишем. Мелкое и самоочевидное — не пишем вообще.
- Один пункт = одно решение + причина (+ реальная цена/риск). Без логов прогонов, замеров, звёзд на GitHub и дат новостей.
- Номера `D<n>` сквозные и не переиспользуются. Потерявшее силу решение помечается «заменено D<m>», а не удаляется молча.

## 1. Что строим

Автоматизированный конвейер «бизнес-задача → проверенный PR» с разделением властей:
Ур.0 Архитектор (декомпозиция) → Ур.1 Спецификатор (тесты + Таблица Истинности) →
Ур.2 Исполнитель (код под замороженные тесты) → Ур.3 Арбитр (споры) →
Ревьюер (PR) → Человек (мерж только руками, всегда).

Экономика: дорогие модели только на входе и выходе, рутина — дешёвые.
Железо: песочница 16 vCPU / 64 GB / 192.168.31.5, всё в docker.

## 2. Решения

### D1. open-swe отклонён как основа, оставлен как референс
- Апстрим перешёл на Managed Deep Agents: бэкенд требует облачный runtime, локальные sandbox'ы выпилены, вендоренный SDK идёт без лицензии → self-host опирался бы на нелицензированный код.
- Самохостящийся MIT-снимок проблемы не решает: фаз/замков/бюджетов в нём нет (это наша задача), а замороженный форк без апстрима — мёртвая ветка.
- Берём из него идеи: структура промптов, reviewer-граф, протокол sandbox-провайдера, UX «задача → PR».

### D2. Исполнитель — OpenHands SDK, aider как дешёвая альтернатива
- OpenHands (MIT, активен): SDK `Agent` + `LLM` + `Conversation` + `Workspace` (Local/Docker/Remote API) + `agent-server` (REST/WS, session keys) — это готовый путь в k8s для проекта №2. Модели — нативно через LiteLLM. Smoke-прогон пройден.
- aider (Apache-2.0): не агент, а правщик диффом + лучшая repo-map (tree-sitter). Гипотеза PoC: **при хорошем плане и замороженных тестах aider кратно дешевле OpenHands** — проверяется сравнением на одних задачах и тестах.
- Слой: OpenHands = runtime/workspace/server, не оркестрация.

### D3. deepagents — harness оркестрации и контекста
- MIT, активен. Даёт: цикл агента, контекст-менеджмент, backends (local/docker/свой), `write_todos`, subagents, middleware, LangGraph (чекпоинты/resume).
- Не даёт: декомпозитор, замки, Таблицу Истинности, PR, UI, учёт денег.
- Роли в архитектуре: (а) оркестратор-граф, (б) обвязка декомпозитора (read-only fs + JSON-схема), (в) запасной исполнитель.
- С D2 не конкурирует — разные слои.

### D4. Модели только через LiteLLM, стоимость считаем сами
- Единственный вход к моделям — LiteLLM, обращение по имени `http://litellm.service/v1` (не по IP).
- Ключ — virtual key только к `llm_api_routes`: `/key/info`, `/spend/logs`, `/budget/list` → 403. Бюджеты ставит владелец в UI шлюза.
- Поэтому расход считаем сами: `usage` из ответа × `input_cost_per_token`/`output_cost_per_token` из `/model/info` (схема учёта — D14).
- Шлюз обслуживает `/v1/chat/completions`, `/v1/responses`, `/v1/messages`; Responses API доступен агентам, которые его требуют.

### D5. Агенты не общаются напрямую (hub-and-spoke)
Любой обмен — только через оркестратор, и он персистит каждое сообщение (карточка + БД). Отсюда аудируемость диалога, отсутствие протечки контекстов между ролями и возможность менять роли по одной.

### D6. Арбитр — отдельная роль, не Hermes и не ревьюер
- Вход: пакет противоречия (утверждение A + контекст, утверждение B + контекст, вывод тестов, дифф, Таблица Истинности).
- Выход: JSON `{winner: A|B|neither, rationale, action: fix_test|fix_code|escalate_human, confidence}`.
- Кода не пишет. Решает, кто прав; при низкой уверенности эскалирует человеку.
- Вендор отличен от Спецификатора и Исполнителя — иначе одинаковые слепые зоны.

### D7. Ревьюер — pr-agent, отдельный процесс
- `The-PR-Agent/pr-agent` (MIT, активен): читает дифф/PR, пишет замечания, в спорах не участвует. Модели — через LiteLLM, провайдеры git: GitHub, GitLab, Gitea, Bitbucket, Azure.
- Работа по URL PR ⇒ нужен git-хостинг с PR. Для пилота выбран GitHub (приватный репозиторий).
- Запускается на песочнице отдельным процессом; ключ LiteLLM в CI не кладём. Выход — комментарий в PR + отчёт, который оркестратор прикладывает к карточке.
- Не пересекается с Арбитром: ревью ≠ арбитраж, разные контексты и модели.

### D8. Доска — Vikunja за тонким адаптером
- Vikunja (AGPL, Go, один контейнер, REST `/api/v1`, kanban-«buckets», метки/комментарии) — достаточно для «окна оркестратора».
- Не Plane (6–8 контейнеров, ~6–8 ГБ, часть сущностей исторически в платной редакции) и не Kanboard (JSON-RPC, архаичный UI, без эпиков).
- Интеграция только через адаптер `board.py`: смена доски = один файл.
- Маппинг: проект = бизнес-задача; колонки Backlog → Plan → Tests → Code → Hardening → Audit → Review → Done; карточка несёт `files_allowed`, контракт, Таблицу Истинности, ветку, стоимость, вердикты.

### D9. Полигон №1 — EVE-дашборд, фреймворк — второй
- EVE: объективная доменная логика (производство, ISK, время) ⇒ тесты проверяют смысл, а не вкус; нет инфраструктуры ⇒ провал атрибутируется пайплайну; требования стабильны; есть мотивация довести до продакшена.
- Фреймворк (k8s + RabbitMQ + UI) — мета-проект: требования ещё не сформулированы, пайплайн отлаживался бы пайплайном. Делать после цифр по EVE.

### D10. Границы роли Hermes
Hermes управляет фазами, запускает процессы, считает деньги, ведёт доску. Ревью и арбитраж — отдельные агенты, к которым Hermes обращается как к сервисам. У каждой из этих ролей свой процесс, свой контекст и своя модель.

### D11. Арбитр двухступенчатый
- Ступень 1 (по умолчанию): прямой вызов LiteLLM без инструментов на «пакет спора». Дёшево, быстро, детерминированный вход.
- Ступень 2 (только при `confidence < 0.6` или `action=need_evidence`): read-only агент по репозиторию (`ls/read/grep`, без записи и запуска кода) — проверить фактическое утверждение.
- Не OpenHands: sandbox и полный агентский цикл избыточны. Если спору нужно *запустить* код — это работа оркестратора (перезапуск тестов), а не арбитра.

### D12. Конфиг ролей — вне репозитория; семь ролей
- `~/.config/cascade/roles.yaml`: у каждой роли своя `model` и `key_ref` (имя переменной с ключом). Переопределения под проект — `~/.config/cascade/projects/<slug>.yaml`; ключи — `~/.config/cascade/keys.env` (0600). Переход на отдельные ключи = правка `key_ref`, без изменения кода.
- Роли и их контракты: **architect** (задача → JSON-план по `plan.schema.json`), **specifier** (подзадача → замороженные тесты + Таблица Истинности), **designer** (UI-подзадача → design spec: сетка, состояния, состав компонентов, дельта токенов; кода не пишет), **executor** (тесты + `files_allowed` → код до зелёного), **arbiter** (пакет спора → `{winner, rationale, action, confidence}`), **reviewer** (PR → отчёт ревью, pr-agent), **vision** (скриншоты и картинки: приёмка отрисованного интерфейса).
- **designer существует только в проектах с интерфейсом** (`ui: true` в конфиге проекта); в остальных роль не оплачивается и не требуется. Разделение: designer интерфейс придумывает, vision проверяет, что он отрисован правильно.
- **Моделей по умолчанию нет**: владелец задаёт их при создании проекта; пустая модель у обязательной роли = проект не готов (`check_project.py` это проверяет). Ориентиры: арбитр ≠ вендор спецификатора и исполнителя, ревьюер ≠ вендор арбитра, исполнитель — самая дешёвая модель, проходящая тесты, дизайнер — сильнейшая доступная модель с картинками. Модель может переопределяться на конкретную задачу с записью факта в карточку.

### D13. Границы репозитория проекта
- В репозитории — только продукт и правила: `AGENTS.md` (индекс «файл | о чём | когда читать»), `.agents/rules/<группа>.md`, `docs/adr/`, код, тесты, CI. Каталог `.cascade/` из репозитория убран.
- Конфиг пайплайна (модели, ключи, бюджеты, гейты, схема плана) — `~/.config/cascade/`. Состояние прогонов (`files_allowed`, фаза, попытки, стоимость) — `~/.local/state/cascade/<slug>/task.json`.
- Причина: смена модели или лимита не должна создавать коммит в продукте; состояние меняется на каждом шаге и у параллельных задач разное — в git ему нельзя (гонки, мусор в диффе).

### D14. Учёт токенов и денег — три уровня, append-only
- Уровни: **проект → фича → задача**. Хранилище — `~/.local/state/cascade/<project>/usage.jsonl`, одно событие на вызов модели (ts, project, feature, task, role, model, input/output tokens, cache_read, cost).
- Почему JSONL, а не один JSON: параллельные агенты пишут без read-modify-write и без гонок, любая сводка считается из лога.
- Инструменты в `~/.config/cascade/bin/usage.py`: `record` (токены; цена по кэшу `pricing.json`, обновление — `price --refresh`), `report [-p проект] [--feature F] [--task T] [--json]`, `projects`. Кэш цен в репозиторий не попадает: он машинный и пересоздаётся из шлюза. Деньги для владельца считает `bin/prices_openrouter.py` по публичному прайсу OpenRouter — шлюзовые цены в отчётах и в репозитории не используются.
- Правило: задача не считается закрытой, пока её вызовы не записаны в ledger и стоимость не приложена к карточке. Валюта — та, в которой биллит шлюз.

### D15. Модель ветвления и ревью
- `main` защищён: только через PR, squash, линейная история. Апрув в GitHub **не требуется** (D19): у соло-владельца автор не может одобрить свой PR, и счётчик апрувов обходился бы только админ-мержем; вместо счётчика — правило «мерж делает человек» и отчёт ревьюера, приложенный к PR.
- `feat/<slug>` — интеграционная ветка фичи, живёт ≤ 1 недели, перебазируется ежедневно. `task/<feat>/<subtask-id>` — атомарные ветки от `feat/*`; PR идёт **в `feat/*`**, не в `main`. Мерж `feat/*` → `main` — один раз, человеком, после полного прогона тестов.
- Один PR = одна подзадача = один `files_allowed`; гейт `check-diff` обязателен.
- Два режима на карточке: `review:agent` (pr-agent → исполнитель правит замечания → авто-мерж в `feat/*` при зелёном) и `review:human` (то же + описание «что/зачем/как проверено» + одобрение).
- Разногласие pr-agent ↔ исполнитель → арбитр; не решено или `confidence < 0.6` → человек.
- Параллельность: только подзадачи с непересекающимися `files_allowed` (проверяет валидатор плана), у каждого агента свой `git worktree`; «горячие» файлы (`__init__.py`, реестры, конфиги) — одному владельцу на итерацию.

### D16. CI — эфемерные контейнерные раннеры на песочнице (заменяет хостовый вариант из прежней редакции)
- Требование: CI исполняет чужой код, поэтому джоба не должна видеть `~/.ssh`, `~/.config/gh` и git-креды. Схема: «одна джоба — один контейнер», раннер `--ephemeral`, registration token берёт хост своим `gh`, PAT внутрь не попадает; egress в LAN из подсети раннера закрыт.
- Архитектурное следствие: CI видит только репозиторий и интернет ⇒ **гейт путей остаётся за оркестратором, локально, до пуша**, а не в CI по локальному состоянию. Серверный замок по `task.json` не строится.
- Ревьюеру раннер не нужен: pr-agent ходит в GitHub и LiteLLM с хоста (D7).
- Как это ставится и обслуживается — скил `github-actions-runner`; runner привязывается к репозиторию проекта при его создании.

### D17. Любое действие пайплайна — скрипт, а не ручной шаг
- Правило: любая операция конвейера выполняется скриптом в `~/.config/cascade/bin/` — передвинуть карточку, завести задачу, отметить usage, запустить исполнителя на подзадаче, собрать пакет спора для арбитра, выставить PR. Ни руками в чате, ни «промптом оркестратора», ни через UI доски.
- Цель: набор скриптов — это **обёртка (API конвейера), поверх которой пишется оркестратор**. Оркестратор ничего не делает сам, он вызывает те же команды, что и человек. Иначе оркестратор пришлось бы писать заново поверх ручных операций, а поведение зависело бы от того, кто запускал шаг.
- Требования к каждому скрипту: неинтерактивный (никаких вопросов и подтверждений), идемпотентный (повтор не ломает состояние), одна операция = один вызов = JSON в stdout, ошибки в stderr, exit 0/1. Состояние — в `~/.local/state/cascade/`, секреты — в `~/.config/cascade/keys.env` (0600), логика — в коде, а не в промптах агентов.
- Следствие для работы: новая фаза конвейера начинается с вопроса «какой скрипт это делает?». Если ответа нет — сначала скрипт, потом прогон. Действие, сделанное руками, считается неавтоматизированным долгом, а не выполненной фазой.
- Что уже в этом виде: `board.py` (создать/перенести/прокомментировать карточку), `validate_plan.py`, `gate.py`, `usage.py`, `check_project.py`. Чего ещё нет: запуск исполнителя на подзадаче (сейчас — ручной прогон OpenHands) — первый кандидат на обёртку, за ним сборка пакета для арбитра и выкладка PR.

### D18. Главный архитектор — роль для вопросов владельца, вызывается человеком
- Восьмая роль `chief_architect` (модель — сильнейшая доступная; обычно та же, что у `architect`, но это две разные роли). Запускает её **только человек**; в фазах конвейера она не участвует, оркестратор сам её не вызывает.
- Отличие от `architect`: архитектор конвейера нарезает одну задачу в JSON-план подзадач с `files_allowed` и проходит валидатор; главный архитектор отвечает на вопрос владельца **текстом** — решение, цена, альтернативы, риски, следующий шаг. Схемы ответа нет, потому что вопрос бывает любой формы.
- Контекст собирает **оркестратор**, а не модель: карта репозитория с правилами и заголовками ADR, контракт схемы БД, роадмап, конкретные файлы. Набор артефактов — решение оркестратора под конкретный вопрос; в промпт попадает только выбранное, а не всё сразу.
- Выход — markdown; вызов пишется в ledger как `-r chief_architect -f _advice`, артефакты — `~/.local/state/cascade/<slug>/advice/`. Скрипт — `chief_architect.py --project <slug> --request "…" --context schema,repo,file:…`.
- Причина: без этой роли владелец спрашивает декомпозитора, который обязан ответить JSON по схеме, и получает нарезку вместо решения; либо архитектурные правки делаются по ходу задач, то есть незаметно и без записи.
- Уточняет счёт ролей из D12: ролей восемь, `designer` по-прежнему существует только в проектах с `ui: true`. Вендорные ограничения D12 (арбитр ≠ спецификатор/исполнитель) к главному архитектору не применяются: он ничего не решает единолично и не ревьюит.

### D19. Финальный мерж — только человек; счётчик апрувов GitHub не используется
- Мерж в `main` делает человек. Ни Hermes, ни ревьюер, ни исполнитель, ни cron не мержат и не апрувят.
- Обязательный апрув GitHub снят: в репозитории одного владельца автор не может одобрить свой PR, поэтому счётчик либо блокировал всё, либо обходился админ-мержем — то есть создавал видимость контроля.
- Что заменяет счётчик: PR открывается с приложенным отчётом ревьюера — находки плюс отдельный список пунктов, которые может решить только человек; правило «мерж руками» проверяется человеком, а не платформой. Ревьюер даёт советы, не блокирует и не мержит.
- Защита ветки `main` сохраняется: только PR, squash, линейная история, force push запрещён. Апрувы не требуются (D15 уточнён).
- Вендорная граница ревьюера (D12) продолжает действовать: ревьюер ≠ арбитр ≠ спецификатор/исполнитель.

### D20. Готовая библиотека предлагается человеку на декомпозиции, а не заменяется самописной
- Правило шага: если задачу закрывает зрелый фреймворк или библиотека, архитектор обязан предложить 2–3 варианта (включая «написать самим») с плюсами, минусами и рекомендацией — до утверждения плана. Решает человек; «предложить» не значит «добавить зависимость».
- Самописный HTTP-сервер, ORM, миграции, планировщик, очередь или auth при наличии стандарта — дефект плана, а не экономия: платим не один раз, а на каждом следующем шаге.
- Зафиксированный владельцем стек — ограничение, а не вопрос. Бэкенд обёртки: FastAPI; данные и миграции: SQLAlchemy + Alembic последних версий; на этапе черновика база — SQLite. Пересмотр стека — отдельное решение, а не побочный эффект задачи.
- Цена: один короткий вопрос в брифе. Риск: правило проверяется человеком на приёмке плана, автоматического гейта нет — ревьюер плана обязан назвать самопис там, где был стандарт.

## 3. Инварианты (нарушать нельзя)

1. Замки проверяет инструмент (гейт `check-diff` у оркестратора + защита ветвей на хостинге), а не промпт.
2. У каждой подзадачи есть `files_allowed`; выход за них = плохой план → перепланировка.
3. Тесты пишет не тот, кто код; тесты замораживаются до начала кодирования.
4. Мерж — только человек.
5. Вендор Арбитра ≠ вендор Спецификатора и Исполнителя; Ревьюер ≠ Арбитр.
6. Один исполнитель в PoC — иначе не понять, что сработало.
7. Каждый вызов модели пишется в ledger; без стоимости в карточке задача не закрыта.
8. Hermes — только оркестратор: не ревьюер и не арбитр.
9. Один PR = одна подзадача = один `files_allowed`.
10. Параллелятся только подзадачи с непересекающимися `files_allowed`, каждая в своём `git worktree`.
11. Нет ручных шагов: каждая операция конвейера — скрипт с JSON-выходом. Сделанное руками не считается сделанным (D17).
